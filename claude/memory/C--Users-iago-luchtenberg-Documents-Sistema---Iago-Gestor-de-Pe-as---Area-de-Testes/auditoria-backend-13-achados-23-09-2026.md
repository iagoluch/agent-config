13. **`catalog_sync_lock` segurava conexão idle-in-transaction** — `app/database/database.py:206` (`catalog_sync_lock`): a aquisição do advisory lock via `SELECT pg_try_advisory_lock` deixava a transação implícita aberta (autocommit off) pela duração inteira do `yield` — se o chamador fizer trabalho demorado dentro do `with`, a conexão do pool fica "idle in transaction" o tempo todo. Corrigido 23/09/2026 por autorização explícita: `connection.commit()` logo após adquirir e logo após liberar o lock. Seguro porque `pg_advisory_lock` (variante *session-level*, não `_xact`) sobrevive a commits na mesma conexão — só é liberado pelo `pg_advisory_unlock` explícito ou fim de sessão, nunca por commit. Achado extra durante a investigação: este método não é chamado em nenhum lugar do código de produção hoje (só no próprio teste `test_advisory_lock_impede_segunda_sincronizacao`) — é infraestrutura dormente, restaurada deliberadamente no release V11 para uso futuro (ver `docs/RELEASE_MANIFEST_V11.txt`), não um bug ativo. Evidência: `tests/test_database_professionalization.py::test_advisory_lock_impede_segunda_sincronizacao` → 1 passed.

## Rejeitado após investigação (achado original estava errado)

6. **Relógio do `_JanelaPrefetch`** — **NÃO aplicar.** `mes/services/management.py` (`_JanelaPrefetch.__init__`, `agora` fixado como `self._agora`) tem comentário explícito: "Congela o 'agora' para que todas as fatias enxerguem o mesmo instante, como CURRENT_TIMESTAMP dentro de uma única consulta." O ponto de construção (`_janela_prefetch`) passa `agora=datetime.now()` de propósito, para espelhar o `COALESCE(data_fim, CURRENT_TIMESTAMP)` do caminho SQL de fallback — não o relógio injetável `self._now()` usado nos limites do filtro. Trocar para `self._now()` NÃO conserta nada: introduziria uma divergência NOVA do caminho SQL sob operação normal (relógio real), o oposto de um fix. O achado original da auditoria estava errado nesse ponto — mantido como está.
